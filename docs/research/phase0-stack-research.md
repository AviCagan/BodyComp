# Phase 0 stack research (2026-09-04)

Condensed output of the research sweep that preceded the Phase 0 build. Each claim carries the researcher's confidence; `verified` means checked against primary sources or reproduced in a scratch project. Kept here so later sessions do not re-derive it. ## react-three-fiber v9 native on Expo SDK 57

Fiber 9.7.0's "@react-three/fiber/native" entry installs cleanly on a real Expo SDK 57 scaffold: `npx expo install expo-gl expo-asset expo-file-system three @react-three/fiber three-stdlib` resolved to expo-gl 57.0.2, expo-asset 57.0.16, expo-file-system 57.0.6, three 0.185.1, fiber 9.7.0, three-stdlib 2.36.1 (plus `npm i -D @types/three@0.185.4`), `npm ls` shows everything deduped with no peer conflicts, expo-doctor passes 21/21, and `tsc` passes (Expo's tsconfig.base has skipLibCheck, which hides a known three-stdlib-vs-@types/three@0.185 .d.ts conflict). Pin three to 0.185.1: it satisfies fiber (>=0.156) and three-stdlib (>=0.128), and every one of the 1,446 named `from "three"` imports in three-stdlib 2.36.1 exists in three 0.185.1. The single most important finding is a Metro dual-package hazard I reproduced with `expo export`: the default SDK 57 config bundles BOTH `three/build/three.cjs` (fiber's native build is CJS and `require('three')` selects the "require" condition) AND `three/build/three.module.js` (your code and three-stdlib `import` it, selecting "import"); that yields the "Multiple instances of Three.js" warning, breaks fiber's applyProps `.copy()` path for Vector3/Euler props, and means fiber's RN polyfills for FileLoader/TextureLoader patch a different three copy than three-stdlib's GLTFLoader uses. A 6-line `resolveRequest` override (`isESMImport:false` for the bare `three` specifier) collapses it to one copy (verified: second export contains only three.cjs). `.glb` files only need `config.resolver.assetExts.push('glb','gltf')` (verified exported asset) and `expo install` auto-adds the `expo-asset` config plugin. With one three copy, `useLoader(GLTFLoader, require('x.glb'))` works because fiber's native entry patches `THREE.FileLoader.prototype.load` to resolve module ids/file:// via expo-asset + `expo-file-system/legacy` `readAsStringAsync(base64)` (legacy still ships in 57.0.6 despite the SDK 55 removal announcement); the polyfill-independent pattern is `Asset.fromModule(m).downloadAsync()` then `new File(localUri).arrayBuffer()` then `GLTFLoader.parse(buffer, '', ok, err)`. Fiber's native events are a PanResponder on an absoluteFill overlay View (click = release within 20px), disabled by `events={null}` plus `pointerEvents="none"` so RNGH can own touches; get state outside the Canvas via `onCreated` (use `state.get()` for fresh values) and raycast with `raycaster.setFromCamera`. `frameloop="demand"` is fine in native: the Canvas wraps `gl.render` to call `endFrameEXP()` after every render and `configure()` invalidates on size changes; no native-specific demand bug is on record. Known issues: New-Arch blank canvas (#3399) fixed in 9.1.3; Expo 54 file-system break fixed in 9.4.2; expo-gl 16.0.9 SIGSEGV on Android (fixed in 16.0.10/SDK 55+, SDK 57 uses 57.0.2); maintainers are moving native out of core into a "pre-alpha, DO NOT USE" @react-three/native for v10 and openly call ExpoGL performance poor, so 9.7.0's in-core native path is best-effort maintained. A dev build is not strictly required (expo-gl is in Expo Go and Expo Go SDK 57 exists), but test a release APK on the Pixel early because release asset paths and the past crash only manifested there. Draco via three-stdlib is not viable in RN (needs `Worker` and, for the wasm path, `WebAssembly`; Hermes still has no WebAssembly per open facebook/hermes#429 and the RN 0.84 blog); skip it or vendor mrdoob's pure-JS draco.js (not on npm) only after device testing. MatCap via `useLoader(THREE.TextureLoader, require('matcap.png'))` goes through fiber's TextureLoader polyfill -> expo-gl `texImage2D({localUri})` decoded by stb_image with flipY honored; set `colorSpace = SRGBColorSpace`, keep to PNG/JPEG, and again this depends on the single-copy fix.

No './package.json' export (require('three/package.json') throws ERR_PACKAGE_PATH_NOT_EXPORTED in Node 22).
- **[verified]** DUAL COPY HAZARD: with the default Expo SDK 57 Metro config (Metro 0.84.5, package exports on by default since Metro 0.82/RN 0.79, condition = 'import' if the importing file used ESM import else 'require'), `expo export -p android` bundles BOTH three/build/three.cjs (pulled by fiber's CJS native build: native/dist/react-three-fiber-native.cjs.prod.js + dist/events-*.cjs.prod.js) AND three/build/three.module.js + three.core.js (pulled by app code and three-stdlib/index.js).
- **[verified]** Forcing a single three copy works: a metro.config.js resolveRequest that resolves the bare 'three' specifier with `{...context, isESMImport: false}` yields a bundle containing only three/build/three.cjs (three-stdlib still resolves). Alternative documented escape hatch is `config.resolver.unstable_enablePackageExports = false` (broader impact).
- **[verified]** Why the dual copy matters: fiber's applyProps only uses target.copy(value) when `target.constructor === value.constructor`, so THREE.Vector3/Euler props created from the other copy fall through and error (this is exactly the 'position props no longer support Vector3' symptom reported alongside 'WARNING: Multiple instances of Three.js being imported' in fiber #3517); also fiber's RN polyfills patch THREE.TextureLoader/FileLoader prototypes on the copy fiber imported, so three-stdlib's GLTFLoader (other copy) would not get the file:// / module-id loading behaviour.
- **[verified]** Metro config for models: `config.resolver.assetExts.push('glb','gltf')` on getDefaultConfig is sufficient; `expo export` listed assets/models/test.glb. No sourceExts changes needed (three-stdlib .js/.cjs and fiber .cjs.js bundled fine). The expo-asset config plugin's `assets` option is only for natively-linked files, not for Metro `require()`d assets.
- **[verified]** Fiber's native entry patches THREE.FileLoader.prototype.load: getAsset(url) passes file: URIs through, unpacks blob:/data: URIs to cache files, otherwise `Asset.fromModule(input).downloadAsync()` and, if the resulting uri has no scheme (Android release), copies it to `${cacheDirectory}ExponentAsset-<hash>.<type>`; then `fs.readAsStringAsync(uri,{encoding:Base64})` -> Buffer -> onLoad(arrayBuffer). It also patches LoaderUtils.extractUrlBase to return './' for non-string urls so numeric module ids work. So `GLTFLoader.load(fileUri)` and `useLoader(GLTFLoader, require('x.glb'))` work on Android via expo-file-system, not via fetch.
- **[verified]** expo-file-system import used by fiber: `require('expo-file-system/legacy')` with fallback to `require('expo-file-system')` (added in fiber 9.4.2 'Expo SDK 54 compatibility through workaround'). expo-file-system 57.0.6 still ships './legacy' (exports map + src/legacy/FileSystem.ts readAsStringAsync) even though Expo's SDK 54 notes said legacy was planned for removal in SDK 55 - that removal did not happen by 57.0.6 (stale claim).
- **[verified]** New File API (SDK 54+): `new File(...uris: (string|File|Directory)[])` accepts `file:///` string URIs; methods `arrayBuffer(): Promise<ArrayBuffer>`, `bytes(): Promise<Uint8Array>`, `bytesSync()`, `base64(): Promise<string>`, `base64Sync()`, `text()`. Legacy alternative: `import * as FileSystem from 'expo-file-system/legacy'; readAsStringAsync(uri,{encoding:'base64'})`.
- **[verified]** On Android, `Asset.fromModule(require('x.glb')).downloadAsync()` yields a `file://` localUri usable by File/readAsStringAsync/expo-gl: expo-asset treats embedded `file:///android_res/` resources as not-downloaded and downloadAsync copies them into the cache directory; in dev the asset is downloaded from Metro.
- **[likely]** Plain three FileLoader (fetch of file://) is not a reliable path on Android/RN (RN 0.82 fetch of local file throws TypeError; expo issue 'Network request failed when fetching a file:// uri'), which is why fiber's polyfill and the File-API + parse() pattern are the known-good routes.
- **[verified]** three-stdlib GLTFLoader signatures: load(url, onLoad, onProgress, onError); parse(data, path, onLoad, onError); parseAsync(data, path). In RN it falls back to TextureLoader for textures because `typeof createImageBitmap === 'undefined'`, so fiber's TextureLoader polyfill applies to GLB-embedded textures too.
- **[verified]** Fiber native event system (9.7.0): Canvas renders <View onLayout style={{flex:1}}> containing <GLView msaaSamples={antialias?4:0}/> (only when measured width>0) and an absoluteFill overlay <View pointerEvents={pointerEvents} {...panHandlers}> whose PanResponder (onStartShouldSetPanResponderCapture/onMoveShouldSetPanResponder all true) dispatches pointerdown/pointermove/pointerup/pointerleave/lostpointercapture and 'click' (on release when hypot(dx,dy) < 20) onto a fake canvas object; coordinates are nativeEvent.locationX/Y mapped to offsetX/Y and NDC = (offsetX/size.width*2-1, -(offsetY/size.height)*2+1). onClick/onPointerDown on <mesh> therefore work in native.
- **[verified]** Disabling fiber's built-in events: pass `events={null}` (Canvas default param only replaces undefined; core configure() does `if (events && !state.events.handlers) state.set({events: events(store)})`, so null means no handlers/no raycast-on-touch) and `pointerEvents="none"` (forwarded to the overlay View) so touches pass to a wrapping RNGH GestureDetector. `events` prop type is a factory function, so use `null as any` in TS.
- **[likely]** RNGH vs fiber Canvas: the overlay claims the RN JS responder (capture handlers return true); a 2024 issue documents responder-nesting problems and a crash when GestureDetector is used inside the Canvas (fiber #3332). Wrapping a plain View around Canvas in GestureDetector with events={null} + pointerEvents="none" avoids the JS responder entirely; RNGH Tap event x/y are 'relative to the view attached to the GestureDetector', so if that View exactly contains the Canvas they map 1:1 to fiber's size (points). Not exercised on a device here.
- **[verified]** Getting R3F state outside Canvas: `onCreated={(state)=>ref.current=state}`; the RootState has camera, scene, gl, raycaster, pointer, size {width,height,top,left}, viewport, invalidate, advance, get, set, setEvents; use `state.get()` for fresh values. `invalidate` (invalidate(state?, frames=1); no arg = all roots), `getRootState`, `_roots`, `useThree`, `useFrame`, `useLoader` are exported from '@react-three/fiber/native'.
- **[likely]** frameloop="demand" in native: the native Canvas overrides onCreated to wrap state.gl.render so `context.endFrameEXP()` runs after every render (so each invalidated frame is presented); core configure() calls invalidate(state) at the end (first frame renders without manual invalidate); the loop uses global requestAnimationFrame; invalidate() coalesces to one queued frame (frames=2 if called inside useFrame). No 2025-2026 issue specific to demand mode on native was found; the general 'invalidate piles frames' bug (#3186) was closed in 2024. Real-device behaviour not tested here.
- **[verified]** Canvas sizing/dpr in native: size comes from onLayout; the root View defaults to flex:1 so the parent must give it height; dpr is forced to PixelRatio.get() ('expo-gl can only render at native dpr/resolution'), so you cannot render at reduced resolution; msaaSamples is iOS-only in expo-gl (no MSAA on Android through this path); gl prop is passed through (avoid an async gl factory: open issue #3782 'Re-render during async gl factory invokes it twice and corrupts the renderer', Jul 2026).
- **[verified]** New Architecture history: fiber #3399 'React native new architecture not showing anything' (Expo 52, 'cannot read trim of undefined') was closed by PR #3539 'fix(native) fix crash on rerendering GLView with new arch', released in fiber 9.1.3 (Jun 29 2025) and confirmed working on Android+iOS new arch by users; 9.3.0 fixed RN 0.79 deep imports; 9.4.2 fixed Expo SDK 54; 9.5.0 added React 19.2 support. expo-gl 15.0.1 converted the iOS view to Swift 'to fix support for the New Architecture'. SDK 55+ removed the legacy architecture entirely.
- **[verified]** Maintenance outlook: fiber maintainer CodyJasonBennett (Jan 2025): 'The issue lies upstream in expo-gl, but Expo themselves are not prioritizing graphics'; in Dec 2025 native issues were redirected to pmndrs/native; that repo's README says native code is being migrated out of r3f core into @react-three/native for R3F v10, 'With SIGNIFICANT performance issues with ExpoGL most of us internally are pretty anti-React-Native', pushing toward react-native-webgpu, and 'Right now its raw, pre alpha and unusable ... DO NOT USE YET'. @react-three/native is not on npm (404). Fiber 9.7.0's in-core /native entry is therefore the supported path today, maintained best-effort.
- **[verified]** expo-gl Android crash: expo-gl 16.0.9 (SDK 54, Dec 2025) crashed with SIGSEGV in expo::gl_cpp::ensurePrototypes() before onContextCreate on Pixel 7/Galaxy A55 (release/preview builds); Expo's tsapeta attributed it to a precompiled binary built against a different Hermes, reported SDK 55 expo-gl 55.0.1 does not crash, and 16.0.10 shipped 2026-01-27. SDK 57 uses expo-gl 57.0.2 (2026-07-15), so it should be unaffected, but verify a release APK on the Pixel because dev builds did not reproduce it.
- **[likely]** 'createProgram'-style errors: no 2025-2026 fiber/expo issue with that text was found; the historical symptoms in this area are 'OES_vertex_array_object extension not supported' (#3082, 2023), 'cannot read trim of undefined' (#3333/#3399, fixed by #3539) and the iOS Simulator never rendering (#2546 closed not-planned, #3528 dup). Physical devices are required for iOS; Android emulators are also discouraged by expo-three docs.
- **[likely]** Dev build vs Expo Go: not strictly required for R3F - expo-gl, expo-asset and expo-file-system are supported in Expo Go and Expo Go lists 'SDK 57 (latest)'; but Expo's SDK 57 changelog noted store approval was pending at release and the historical crash and asset-path differences only appear in release builds, so use a dev client and test a release APK early.
- **[verified]** Reanimated/expo-gl: expo-gl 16.0.0 added react-native-reanimated as an OPTIONAL peer (for its experimental worklet GL API); the 2023 'GLView.getWorkletContext is not a function' issues only concern that worklet API, which fiber does not use. Expo docs: third-party libraries like Three.js cannot run inside worklets, so R3F stays on the JS thread; bridge Reanimated values with useAnimatedReaction + scheduleOnRN (react-native-worklets 0.10.1 exports scheduleOnRN and runOnJS-as-wrapper; Reanimated 4.5.1 re-exports runOnJS as deprecated). Reading sharedValue.value on the JS thread is allowed but blocks until fetched from the UI thread.
- **[verified]** Draco in RN is not viable with three-stdlib's DRACOLoader: it spawns `new Worker(URL.createObjectURL(new Blob([body])))`, loads draco_decoder.js / draco_wasm_wrapper.js / draco_decoder.wasm from decoderPath via FileLoader, and only picks the JS decoder when `typeof WebAssembly !== 'object'` or decoderConfig.type==='js' - but still inside a Worker, which React Native/Hermes does not provide. Hermes has no global WebAssembly: facebook/hermes#429 'WASM support within Hermes?' is still open and the official RN 0.84 'Hermes V1 by default' post says nothing about WebAssembly (third-party posts claiming WASM in 0.84 are unverified).
- **[verified]** Pure-JS Draco fallback: mrdoob/draco.js is a drop-in DRACOLoader (no Worker, no WASM, no fetch; ~20KB gzipped; triangle meshes only; Draco bitstream 2.2; declares dependency three ^0.182.0) used via `gltfLoader.setDRACOLoader(new DRACOLoader())`. It is NOT published under 'draco.js' on npm (that name is an unrelated 1.0.1 package), so it would have to be vendored from ./build/DRACOLoader.js; untested in Hermes/RN. Given the brief says Draco is optional, skip it and rely on gltf-transform quantize/prune/weld instead.
- **[likely]** MatCap texture path: fiber's native TextureLoader polyfill -> getAsset(require(png)) -> Image.getSize -> texture.image = {data:{localUri}, width, height}, flipY=true ('Since expo-gl@12.4.0'), isDataTexture=true (forces the non-DOM upload); expo-gl texImage2D reads `localUri` (must start with file://), decodes with stb_image (PNG/JPEG only since 16.0.9 - GIF/BMP/TGA/PSD/HDR removed) and flips rows when UNPACK_FLIP_Y_WEBGL is set. So `useLoader(THREE.TextureLoader, require('../assets/matcap.png'))` + `<meshMatcapMaterial matcap={tex}/>` is the expected working pattern; set `tex.colorSpace = THREE.SRGBColorSpace`. Data URIs are supported by being written to cache first; ImageBitmap is never used. Device-level appearance not verified here and it depends on the single-three-copy fix.
- **[verified]** TypeScript: three-stdlib 2.36.1 .d.ts is incompatible with @types/three@0.185 (SVGLoader/TGALoader errors; fixed by three-stdlib PR #433 on 2026-06-26 but no release after 2.36.1 exists), yet Expo's tsconfig.base sets skipLibCheck:true, so `tsc --noEmit` in the scaffold (App.tsx importing @react-three/fiber/native, three-stdlib, expo-file-system File, three) passed with 0 errors; fiber resolves types via native/package.json 'types' (no root exports map).
- **[likely]** three >= r163 requires WebGL2; expo-gl exposes WebGL2 on GLES3 devices and Expo recommends checking `gl instanceof WebGL2RenderingContext` because 'Some older Android devices may not support WebGL2 features'. A Pixel is fine; very old Android devices may fail to create the renderer.

## Gestures: RNGH 2.32 + Reanimated 4.5 driving R3F

Recommendation for the MuscleMap gesture layer on Expo SDK 57 (RNGH 2.32.0 + Reanimated 4.5.1 + @react-three/fiber 9.7.0 + three 0.185): use ONE Gesture.Pan (minPointers 1, maxPointers 2, averageTouches(true)) that branches on e.numberOfPointers with delta-based updates (1 finger = orbit, 2 fingers = vertical pan), composed as Gesture.Race(Gesture.Exclusive(doubleTap, singleTap), Gesture.Simultaneous(pan, pinch)). The two-Pan variant (maxPointers(1) + minPointers(2)) also works on Android because RNGH 2.32's PanGestureHandler.kt calls cancel() on an ACTIVE pan when pointerCount exceeds maxPointers, but the single-Pan variant gives seamless 1<->2 finger transitions and never leaves a "dead" finger. Tap select = Gesture.Tap().maxDuration(250).maxDistance(8); it can never fire mid-drag because Pan activation (Android touch slop, ~8 dp) cancels the Race siblings and maxDistance(8) fails it anyway. Exclusive(doubleTap, singleTap) delays single-tap by the double-tap's maxDelay; the real default is 200 ms on both Android and iOS in 2.32.0 (the docs' "500" is stale) - set .maxDelay(250) explicitly and note that Android measures Tap maxDistance from the FIRST tap's start across the whole sequence, so give the double-tap a looser maxDistance (~24 dp). Inertia: withDecay on a yaw shared value expressed in DEGREES (not radians) because Reanimated 4.5.1 stops decay when |v| < VELOCITY_EPS = 1 unit/s (57 deg/s in radians = visible jolt); rigidDecay compounds velocity with exp(-(1-d)*(now-start)*0.1) every frame, so time-to-rest is frame-rate dependent: for typical flings (500-2000 deg/s) deceleration 0.999 rests in ~1.4-1.6 s at 60 Hz but ~1.0-1.1 s at 120 Hz (Pixel "Smooth Display" on); 0.9995 gives ~1.5 s at 120 Hz. If you need an exact, refresh-rate-independent 1.5 s, use withTiming(yaw + 0.5*v0, {duration:1500, easing: Easing.out(Easing.cubic)}) which has the same initial slope and nearly identical travel. Snaps: withTiming(..., {duration: 300}) on yaw (shortest arc), pitch, dist, panY; cancelAnimation on all four in pan.onBegin (touch-down, pre-activation). Bridging: reading sv.value on the JS thread is allowed but, in 4.5.1, when the value is dirty it performs a blocking runOnUISync round-trip (docs: "the thread will get blocked until the value is fetched from the UI thread"), so reading four values in useFrame every frame is the worst option and still needs a trigger; instead use useAnimatedReaction over the four values and scheduleOnRN(pushPose, yaw, pitch, dist, panY) (runOnJS is deprecated in 4.x but still exported) into a module-level plain object plus invalidate(); with frameloop="demand" each push sets internal.frames=1 and restarts R3F's rAF loop, so UI-thread decay/timing animations keep rendering with exactly one cross-thread call per UI update and zero allocations on the three.js side (the 4-slot tuple in prepare is the only per-update allocation, on the UI runtime). JS-side colour lerps keep themselves alive by calling invalidate() inside useFrame (sets frames=2). Raycast on tap: RNGH x/y are dp relative to the detector view and R3F native's size comes from onLayout in dp, so NDC = (x/size.width*2-1, -(y/size.height*2-1)) with no PixelRatio term (R3F sets gl.setPixelRatio(PixelRatio.get()) and drawing buffer = dp x dpr, which only matters if you use drawingBufferWidth); use raycaster.setFromCamera + intersectObjects(meshes, false, reusedArray) and mesh.name. Put pointerEvents="none" on <Canvas>: R3F native forwards that prop to its PanResponder overlay View only, which disables R3F's own touch events and per-move JS raycasts and avoids the documented responder conflict (pmndrs #3332). MeshMatcapMaterial has no emissive; outgoing colour is diffuse*matcap, so highlight by lerping material.color toward white (or use an onBeforeCompile uEmissive injection at 'vec3 outgoingLight = diffuseColor.rgb * matcapColor.rgb;'), dim others via color.copy(base).multiplyScalar(0.7), animate with color.lerpColors(from, to, t) over 400 ms using per-region material clones and pre-allocated THREE.Color scratch. Camera: fov 30 deg vertical, target (0, 0.5, 0), d = H/(2*fill*tan(fov/2)) = 2.87 for fill 0.65; clamp dist to [1.43, 4.6] and panY to +-0.35.

### Findings

- **[verified]** RNGH 2.32.0 JS API names are exactly: Tap: numberOfTaps, maxDuration, maxDelay, maxDistance, maxDeltaX/Y, minPointers; Pan: minPointers, maxPointers, minDistance, averageTouches, activateAfterLongPress, activeOffsetX/Y, failOffsetX/Y; base: onBegin, onStart, onUpdate, onChange, onEnd(event, success), onFinalize(event, success), onTouchesDown/Move/Up/Cancelled, enabled, shouldCancelWhenOutside, hitSlop, runOnJS, manualActivation, withRef, simultaneousWithExternalGesture, requireExternalGestureToFail, blocksExternalGesture; composition Gesture.Race / Simultaneous / Exclusive.
- **[verified]** Composition semantics: Race - 'Only one of the provided gestures can become active at the same time. The first gesture to become active will cancel the rest'; Simultaneous - 'All of the provided gestures can activate at the same time'; Exclusive - 'Only one ... with the first one having a higher priority'. Docs example: const taps = Gesture.Exclusive(doubleTap, singleTap).
- **[verified]** Android PanGestureHandler (2.32.0): when a new pointer goes down and pointerCount > maxPointers, an ACTIVE handler is cancel()ed (BEGAN -> fail()); when a pointer lifts and count < minPointers while ACTIVE it fail()s; on every POINTER_DOWN/UP the translation offset is re-based (offsetX += lastX - startX) so translationX/Y stays continuous across finger-count changes (with averageTouches the centroid is used). Default minDistance = ViewConfiguration.scaledTouchSlop; maxPointers default 10.
- **[verified]** Tap defaults in 2.32.0 are maxDuration 500 ms and maxDelay 200 ms on BOTH Android and iOS (the 2.x docs say maxDelay default 500 - stale). maxDistance has no limit by default (Android MAX_VALUE_IGNORE, iOS NAN) and is specified in dp (converted with PixelUtil.toPixelFromDIP). For multi-tap, Android sets startX/startY only while UNDETERMINED, so maxDistance is measured from the first tap's touch-down across the whole double-tap sequence.
- **[verified]** GestureDetector auto-uses worklets: 'GestureDetector will decide whether to use Reanimated to process provided gestures based on callbacks they have. If any of the callbacks is a worklet, tools provided by Reanimated will be utilized'. Mixing worklet and non-worklet callbacks throws unless .runOnJS(true); all-non-worklet callbacks only warn. GestureHandlerRootView must be near the app root; relations only work under the same root view. babel-preset-expo in SDK 57 configures the worklets Babel plugin automatically.

### Open questions

- Refresh-rate policy: Pixel 8/9 run at 60 Hz unless 'Smooth Display' is on (120 Hz). Reanimated 4.5.1's withDecay rests ~35% sooner at 120 Hz for the same deceleration. Decide between withDecay(deceleration 0.999, accept 1.0-1.6 s variance) or the deterministic withTiming(yaw + 0.5*v0, 1500 ms, Easing.out(cubic)) inertia; consider filing/checking an upstream issue on the compounding formula before relying on exact timings.
- Double-tap latency: Exclusive(doubleTap, singleTap) delays region selection by maxDelay (~200-250 ms). Is that acceptable, or should single-tap fire immediately with a manual 'second tap within 250 ms => reset view' check (which would briefly select a region before resetting)?
- Asset forward axis: the yaw constants assume the model faces +Z (glTF convention); if the exported body faces -Z, swap YAW_LEFT/YAW_RIGHT and negate the camera x term.
- Raycast cost on the JS thread depends on the final triangle count per region mesh; three.js brute-force raycasting is fine up to a few tens of thousands of triangles but three-mesh-bvh may be needed beyond that (not validated on React Native / Hermes here).
- pointerEvents="none" on <Canvas> removes R3F's own pointer events entirely (mesh onClick/onPointerOver, onPointerMissed). Confirm nothing else in the product needs them; otherwise a custom `events` factory would be required and the RNGH conflict from pmndrs/react-three-fiber#3332 re-appears.
- iOS behaviour is unverified in this environment (no Mac): in particular UIPanGestureRecognizer's handling of maximumNumberOfTouches if the team ever switches to the two-Pan variant, and the exact iOS Pan minimum distance. The single-Pan design avoids the first concern.
- No device/emulator was available: the end-to-end path (RNGH detector as ancestor of expo-gl's GLView receiving touches when the R3F overlay has pointerEvents='none') is standard RNGH ancestor dispatch but should be smoke-tested on the Pixel first.
- If the app later adopts RNGH 3.x (latest 3.2.1) or Reanimated 4.6 (needs worklets 0.12), re-check: Reanimated's deprecated runOnJS re-export is slated for removal, and RNGH 3 may change defaults/APIs; the SDK 57 template pins (RNGH ~2.32, Reanimated 4.5.1, worklets 0.10.1) are what this research targets.

Recommendation for MuscleMap on Expo SDK 57 (expo 57.0.19, RN 0.86.3, React 19.2.3): pin typescript ~6.0.3 (the template pin) and do NOT move to typescript 7.0.2 yet — TS 7 (GA 2026-07-08) ships no JS API, so @typescript-eslint (peer typescript <6.1.0, pulled in by eslint-config-expo 57) and ts-jest (<7) cannot run on it; I confirmed `tsc --noEmit` 7.0.2 does work against expo/tsconfig.base, but that only buys you a faster type-check at the cost of a split toolchain. expo/tsconfig.base for SDK 57 (module preserve, moduleResolution bundler, esModuleInterop true, customConditions ["react-native"], no baseUrl) already contains zero TS-6-deprecated options, so no ignoreDeprecations is needed; just never add baseUrl (TS 6 error TS5101, TS 7 hard error TS5102 — the Expo TypeScript guide still shows baseUrl and is stale) and add "types": ["jest"] because TS 6 defaults types to [] (verified: describe/it/expect become TS2593 otherwise). jest-expo 57 uses Babel, and @expo/cli parses tsconfig with JSON5, so neither depends on the TS version. ESLint: use eslint 9.39.x (npx expo lint installs ^9.0.0 and requires >=8.57; eslint-config-expo 57's transitive eslint-plugin-import/react peers stop at ^9, so ESLint 10.9.1 would produce peer conflicts) with the flat config from @expo/cli's template plus eslint-config-prettier/flat, and run prettier --check separately. Jest: jest-expo 57.0.5 is built on Jest 29 (babel-jest/jest-environment-jsdom ^29) and needs @react-native/jest-preset 0.86.3 installed explicitly (its jest-preset.js throws otherwise); `npx expo install jest` does not pin jest (not in bundledNativeModules), so pin jest 29.7.0/@types/jest 29.5.14, RNTL 14.0.1 + test-renderer 1.2.0. Use a two-project jest.config.js: an `app` project on the jest-expo preset (reanimated setUpTests + worklets mock + gesture-handler jestSetup + manual expo-sqlite/expo-crypto mocks) and an `engine` project with testEnvironment node and babel-jest only — I ran that engine project here on Node 22: three 0.185.1 (CJS build), three-stdlib 2.36.1 (CJS), drizzle-orm 0.45.2 and zustand/vanilla all import and run in ~1.3 s; only `three/examples/jsm/*` (ESM-only) needs `three` allow-listed in transformIgnorePatterns. expo-router 57: keep "main": "expo-router/entry", a "scheme", experiments.typedRoutes (still beta/off by default; `npx expo customize tsconfig.json` regenerates .expo/types/router.d.ts without a dev server — verified in @expo/cli source, so run it in CI before tsc); the SDK 57 template now uses src/app and NativeTabs from expo-router/unstable-native-tabs (alpha; Android max 5 tabs) — JS <Tabs> in app/(tabs)/_layout.tsx remains the stable choice. New Architecture cannot be disabled: RN 0.82+ ignores newArchEnabled=false and Expo docs say SDK 55+ "do not support disabling", so there is no legacy fallback for expo-gl/fiber problems. EAS: a free plan still exists (15 Android + 15 iOS builds/month, 1 concurrency, 45-min timeout, medium workers, low-priority queue that often waits 1h+ at US peak); default Android image is ubuntu-26.04-jdk-17-ndk-r27b-sdk-57 with Node 22.23.1, so use Node 22 in CI; `eas build --local` is not supported on Windows (WSL only); iOS signing and `eas submit --platform ios` (App Store Connect API key) work from Windows/Linux, no Mac needed, but a paid Apple Developer account is required. Local Android on Windows needs Android Studio + JDK 17 + SDK Platform 36 + ANDROID_HOME, then `npx expo run:android`. GitHub Actions needs no expo-github-action for a CI-only workflow (it just installs/authenticates expo/eas CLIs); plain actions/checkout@v5 + actions/setup-node@v6 (cache: npm) suffices. Hermes V1 is the engine in RN 0.86; Intl is partial (Collator/NumberFormat/DateTimeFormat, no PluralRules/RelativeTimeFormat/ListFormat/Segmenter) and there is no global `crypto` on device (RN core, Hermes and Expo's winter runtime all lack it) even though Node/Jest have it — use expo-crypto's randomUUID() (or a getRandomValues polyfill for third-party libs) behind a tiny id helper.
